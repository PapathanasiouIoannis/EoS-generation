# Contributing

Contributions are welcome. Scientific correctness and reproducibility take
priority over code cleanup, runtime, or visual smoothness.

By participating, contributors agree to follow the
[`CODE_OF_CONDUCT.md`](CODE_OF_CONDUCT.md). Suspected security vulnerabilities
must be reported privately according to [`SECURITY.md`](SECURITY.md), not in a
public issue.

## Before changing code

1. Read the [scientific boundary](README.md#scientific-boundary) and the
   relevant guide under [`docs/`](docs/).
2. Trace the public entry point, private implementation, configuration
   expansion, and focused tests involved in the change.
3. Start from a clean, current `main` and create one focused branch.
4. Keep unrelated local results and user files out of the diff.

The supported user surfaces are the compatibility command `bsk24-trial`, the
model-specific notebooks under `notebooks/`, the files under `configs/`,
and the objects exported from `eos_generation`. The command and public Python
API support legacy BSk24 settings and the explicit frozen CFL matter model;
the separate CFL notebook uses that same governed API. Preserve legacy BSk24 serialization,
hashes, case IDs, and behavior unless a deliberate breaking release has been
agreed.

## Scientific changes

Document all of the following in the pull request:

- the physical quantity, units, normalization, and valid domain;
- whether energy density includes rest-mass energy;
- every equation, coefficient, physical constant, gate, solver setting, or
  numerical tolerance that changes;
- the independent reference or benchmark supporting the change;
- the result fields and plots that may be affected.

For CFL changes, also state whether the pure bare self-bound scope, frozen
parameter hash, formula-derived binary64 domain, finite-density surface,
external two-flavor assumption, or exact-once tidal jump evidence is affected.
The frozen microphysical constants are not sweep parameters. Publication-level
CFL stellar claims require strict convergence, a convention-matched published
benchmark, and comparison with an independent solver.

Do not silently extrapolate, repair an invalid proposal, weaken an acceptance
condition to pass a test, or describe a numerical seam as a physical
transition. New reference fixtures must not be generated by the implementation
they are intended to test.

## Development workflow

Install the development checkout and notebook tools:

```powershell
conda env create -f environment.yml
conda activate eos-generation
python -m pip install -e ".[notebook]"
python -m pytest -q
```

Use the narrowest relevant test while developing. Before opening a pull
request, run the full focused suite, build a wheel, and check the installed
command from outside the checkout:

```powershell
python -m pip install build
python -m build --wheel
python -m pip install --force-reinstall dist/eos_generation-1.2.0-py3-none-any.whl
bsk24-trial --help
```

Routine verification may execute passive plans. Do not launch a stellar run
merely to inspect imports, documentation, packaging, or notebook passivity.

## Configuration and provenance

The public JSON fields are governed by [`configs/schema.json`](configs/schema.json)
and explained in [`docs/parameters.md`](docs/parameters.md). Named precision
profiles expand to immutable internal numerical settings. Change those
profiles only as a scientific change, and retain the expanded settings in the
saved result.

Omitted `matter_model` is the legacy BSk24 identity; CFL must be explicit and
use the surface anchor. Do not migrate old settings by inserting a default
field, and do not duplicate the frozen CFL profile in configuration or
planning code.

When adding or moving an active source module, update the source-provenance
inventory and its regression test. Result validation must remain read-only,
and planning must continue to make zero solver calls and zero filesystem
writes.

## Pull requests

- Stage only intended files.
- Summarize user-visible and scientific behavior separately.
- Include the exact test commands and results.
- Call out unresolved numerical or physical questions.
- Wait for `.github/workflows/ci.yml` to pass; do not bypass required checks.
